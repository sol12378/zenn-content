# Claude Code のAIチームでLLMの品質を自動でチェックしてみたよ！

やあ！みんな！探求者のケイだよ！

AIを業務に使い始めたはいいけど、「本当にこの出力、信頼していいの…？」って不安になったことない？毎回ちゃんと動いてると思ったら、突然おかしな答えが出てきて、しかもそれを誰も気づかないまま本番に流れてた——なんて経験、君だけじゃないよ。

今日はそんな「AIの出力品質、どうやって守るの問題」を、**Claude Code Agent Teams**（AIの専門家チーム）でハックする方法を解説するよ！

---

## 絶望の現実：AIに任せたら、誰が品質を見てくれるの？

正直に言おう。AIを業務に組み込もうとすると、こういう地獄が待ってるんだ。

**地獄1: 「全部信じてたら大変なことに」**
あるデータ分析チームは、AIに毎月のCSV集計を任せてた。数ヶ月後、集計ロジックが「売上を重複カウント」していたことが発覚。経営層へのレポートが全部間違ってた。AIが黙って嘘の数字を出し続けてて、誰も気づかなかった。

**原因**はシンプル。単一のAIに全部丸投げして、出力の正しさを確かめる仕組みが何もなかったから。

**地獄2: 「人間チェックが追いつかない」**
ある金融機関は、AIで与信判定文を生成して、営業が目視で確認するフローを作った。でも件数が増えるにつれてチェックが追いつかなくなり、最終的に不正な与信文書が流通してしまった。

**原因**はフィードバックループの断絶。品質チェックが「人間の目」だけに依存してた。

**地獄3: 「複数AIを使ったら、バラバラになった」**
ある会社が、商品説明にClaude、在庫最適化にGPT、顧客対応にBertを使い分けた。それぞれの出力フォーマットが違いすぎて、データをまとめようとするたびにエラーが出まくった。

**原因**は共通の品質基準がなかったこと。AIたちが「共通言語」なしに勝手に動いてたんだ。

---

君の失敗じゃない。「AIの品質を保証する仕組み」を誰も教えてくれなかっただけだ。そこが今日、変わるよ。

## 敵の正体：なぜLLMは品質が安定しないのか

LLMの出力が不安定な理由を、まず論理的に理解しよう。

LLMは本質的に**確率的なシステム**なんだ。つまり「工場の自動機械」みたいに毎回同じ結果を出す設計になってない。同じプロンプトを入れても、少しずつ違う答えが返ってくる——それが仕様だ。

さらに、LLMは「正しいかどうか」より「もっともらしいかどうか」で言葉を選ぶ。これがハルシネーション（AIが自信満々に嘘をつく現象）の原因になる。

つまり問題はこうだ：

- AIは「ミスをしてはいけない」という概念を持っていない
- ミスをしても、自分でそれに気づくことができない
- だから誰かが「チェック役」にならないといけない

でも人間がその役割を担うと、スピードが出ない。AIを入れたのにボトルネックになる。

**じゃあ、AIがAIをチェックしたらどうだろう？**

## パラダイムシフト：「気合でチェック」をやめて、「AIチームで自動化」する

ここが今日のコアアイデアだよ。

従来の発想：**1つのAIが生成 → 人間がチェック → 次へ**
新しい発想：**AIチームが生成・検証・採点まで自動で回す**

「エージェント（Agent）」って聞いたことある？これは「特定の役割を持ったAI」のことなんだ。魔法の翻訳をすると——

> **エージェント = 専門家チームの各メンバー**

工場でいえば、製造担当、検品担当、最終確認担当がいるよね。**Claude Code Agent Teams** は、まさにそれをAIでやる仕組みなんだ。

```
入力データ
  ↓
┌─────────────────────────────────────┐
│ データ抽出エージェント               │
│ （CSVを解析し、構造化データに変換）  │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│ 品質検証エージェント（複数）          │
│ ・形式妥当性チェック               │
│ ・ビジネスルール検証               │
│ ・異常値検知                      │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│ スコアリングエージェント             │
│ （品質スコア = 各検証結果の集約）   │
└──────────────┬──────────────────────┘
               ↓
出力（品質スコア + アラート）
```

このフローを「パイプライン（= 工場の生産ライン）」と呼ぶよ。材料が流れてきて、各ステーションで加工・検査されて、完成品になる——その仕組みをAIで作るんだ。

複数エージェントが強い理由は3つある：

1. **独立した視点**：形式担当、ビジネスロジック担当、安全性担当が別々にチェックするから、単体では見落としやすい問題を検出できる
2. **スケール対応**：ルールが増えても「新しい担当エージェントを追加するだけ」で済む
3. **説明責任**：なぜ拒否したかのログが残るから、AIの判断がブラックボックスにならない

## 超実践：ECサイトの商品説明を自動品質チェックする

具体例で見てみよう。毎日1,000件の商品説明を自動生成するECプラットフォームを想像して。

**品質の課題**：
- 商品名が正確に入ってるか
- 素材・サイズ・色などの特性が漏れてないか
- 「世界最高」みたいな根拠のない誇大表現がないか
- JSON形式（= データの入れ物）が正しく出力されてるか

これを人手でやったら数日かかる。AIチームに任せよう。

### Agent Teams による自動検証パイプライン

```python
# 疑似コード

class CommerceQualityPipeline:
    """
    商品説明の品質検証パイプライン
    複数エージェントが協調して品質を検証
    """

    def __init__(self):
        # 各検証エージェントを初期化
        self.description_generator = Agent(model="claude-opus", role="description_generator")
        self.validator_format = Agent(model="claude-3.5-sonnet", role="format_validator")
        self.validator_business = Agent(model="claude-3.5-sonnet", role="business_logic_validator")
        self.validator_safety = Agent(model="claude-3.5-sonnet", role="safety_validator")
        self.scorer = Agent(model="claude-3.5-sonnet", role="quality_scorer")

    def process_product(self, product_data):
        """
        商品1件をパイプラインで処理
        """

        # Step 1: 説明文の生成
        description = self.description_generator.run(
            prompt=f"""商品データから説明文を生成してください。
            商品ID: {product_data['id']}
            商品名: {product_data['name']}
            カテゴリ: {product_data['category']}
            仕様: {product_data['spec']}

            出力形式:
            {{"description": "説明文", "keywords": ["キーワード1", "キーワード2"]}}
            """
        )

        # Step 2: 形式妥当性チェック（JSON形式、必須フィールド等）
        format_check = self.validator_format.run(
            prompt=f"""以下の出力が正しいJSON形式か、必須フィールドを含むか検証してください。
            出力: {description}

            検証結果を以下の形式で返してください:
            {{"is_valid": true/false, "errors": ["エラー1", "エラー2"]}}
            """
        )

        if not format_check['is_valid']:
            return {
                "product_id": product_data['id'],
                "quality_score": 0,
                "status": "rejected",
                "reason": f"形式エラー: {format_check['errors']}"
            }

        # Step 3: ビジネスルール検証
        business_check = self.validator_business.run(
            prompt=f"""以下の説明文が、商品の主要特性をカバーしているか確認してください。
            商品名: {product_data['name']}
            商品仕様: {product_data['spec']}
            生成説明文: {description['description']}

            チェック項目:
            - 商品名が説明文に含まれているか
            - 主要素材・サイズが記載されているか
            - 価格帯や適用範囲が明示されているか

            結果: {{"coverage": 0-100, "missing_items": ["項目1", "項目2"]}}
            """
        )

        # Step 4: 安全性チェック（不当な主張、差別表現等）
        safety_check = self.validator_safety.run(
            prompt=f"""以下の説明文に、不適切な表現がないか確認してください。
            説明文: {description['description']}

            チェック項目:
            - 医療効果・法的根拠なき主張
            - 差別的表現
            - 誇大広告（根拠なき「最高」「唯一」等）
            - 事実に反する記述

            結果: {{"is_safe": true/false, "issues": ["問題1", "問題2"]}}
            """
        )

        # Step 5: 総合スコアリング
        quality_score = self.scorer.run(
            prompt=f"""複数の検証結果から、商品説明の総合品質スコア（0-100）を算出してください。

            検証結果:
            - 形式妥当性: {format_check}
            - ビジネス対応率: {business_check['coverage']}
            - 安全性: {safety_check['is_safe']}

            スコア計算式:
            - 形式OK: +25点
            - ビジネス対応率 > 80%: +35点
            - 安全性OK: +40点

            結果: {{"score": 0-100, "recommendation": "approved/review_needed/rejected"}}
            """
        )

        return {
            "product_id": product_data['id'],
            "quality_score": quality_score['score'],
            "status": quality_score['recommendation'],
            "validation_details": {
                "format": format_check,
                "business": business_check,
                "safety": safety_check
            }
        }

# 実行例
pipeline = CommerceQualityPipeline()
products = load_products_from_api()

results = []
for product in products:
    result = pipeline.process_product(product)
    results.append(result)

    if result['quality_score'] < 70:
        alert_team(f"商品 {product['id']}: 品質スコア {result['quality_score']} - 手動確認が必要")

# 品質スコアの集計
avg_score = sum(r['quality_score'] for r in results) / len(results)
print(f"本日の平均品質スコア: {avg_score}")
```

### 実装で特にカッコいいポイント

**品質スコア（= テストの採点結果）**という概念がキモだよ。

各エージェントが独立してチェックして、最後に「形式+ビジネスロジック+安全性」を足し算してスコア化する。これ、学校のテストと同じ発想なんだ。国語・数学・英語を別の先生が採点して、合計点で合否を判定するイメージ。

- 形式チェック担当エージェント → 「構造が正しいか」を確認
- ビジネスルール担当エージェント → 「内容が実態に合ってるか」を確認
- 安全性担当エージェント → 「問題のある表現がないか」を確認

3つの視点が揃って初めて「品質OK」の判定が出る仕組みだ。

## フィードバックループ：スコアを「改善の燃料」にする

品質スコアって、出して終わりじゃないんだ。ここが本当に重要なポイント。

```
品質スコア（定量データ）
  ↓
「なぜスコアが低いのか」の分析
  ↓
エージェントの検証ルールの改善
  ↓
LLMプロンプトの最適化
  ↓
再度パイプラインで検証
  ↓
スコア向上の確認
```

各エージェントの判断理由がログとして残るから、「形式エラーが多い」「商品特性の抜け漏れが頻繁」みたいな具体的な改善ポイントが浮かび上がってくる。

これって、スポーツのビデオ分析と同じだよ。試合の録画を見て「この場面でのパスが問題だった」と分析して、次の練習に活かす——AIパイプラインでも全く同じことができるんだ。

## 未来のビジョン：君はもう「作業者」じゃなく「アーキテクト」だ

ここまで読んでくれた君に、最後に一番大事なことを伝えたい。

「AIの出力を人間がチェックする」という時代は終わりつつあるんだ。次の時代は**「AIチームの品質管理システムを設計する人間」**が価値を持つ。

今日紹介した仕組みは、実は「AI品質監査（AI Audit）」という、もっと大きな世界への入口でもあるんだ。

- **適合性監視**：企業ポリシーや法令に沿ってるかを継続的にチェック
- **性能監視**：意図した精度が保たれてるかを計測
- **リスク監視**：事業上の致命的なミスが起きてないかを検知

これは「泥縄式のチェック」じゃなく、**組織全体でのAI信頼性運用**へのステップアップだよ。

複数エージェントによる多軸的な品質検証——この考え方を体系的に拡張すれば、複数部門・複数LLMの品質を統一的に監視する仕組みになる。それが **MAGI Audit** のようなAI品質監査プラットフォームが目指してる世界だ。

本記事で示したパイプラインを「コードで書いた実験」とすれば、次のステップは「それを組織の運用フレームワーク」として育てることなんだ。
