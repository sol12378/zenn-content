## 🧭 MAGI Platform は何をするもの？

MAGI Platform は、AIコーディングツールのための 管制塔 だよ。

Claude Code、Codex、Cursor みたいなツールは、今やエンジニアの手足になりつつある。  
でも、利用が増えるほど、いろんな情報がバラバラになってしまう。

どのモデルを使ったのか。  
どれくらいトークンを消費したのか。  
いくらコストが発生したのか。  
どのプロジェクトで使ったのか。  
どのブランチで作業したのか。  
PRにどれくらい紐づいているのか。  
エラーや中断はどこで起きたのか。

MAGI Platform は、これらをひとつのダッシュボードに集める。

つまり、AI開発の「見えない活動ログ」を、レントゲン写真みたいにくっきり映し出すツールなんだ。

## 💰 Claude Code のコストを見える化する

まず見てほしいのが、Claude Code レポートだよ。

![Claude Code レポート](/images/am-magi-platform-launch/claude-code-report.png)

この画面では、Claude Code の利用状況を一目で確認できる。

今回のデータでは、推定コストは $817.69。  
日本円では、およそ 122,654円 だね。

作業時間は 16,471分。  
編集回数は 584回。  
PRは 12件。

ここで面白いのは、単に「使った金額」だけじゃなくて、キャッシュ効率も見えるところなんだ。

キャッシュのヒット率は 96.4%。  
推定削減額は $4,511.40。

これはすごい数字だよ。

もしキャッシュがなかったら、もっと大きな請求になっていたかもしれない。  
つまり、プロンプトキャッシュは AI開発における節約の魔法 なんだ。

分厚い設計書を、毎回ゼロから読ませるんじゃない。  
一度読ませた内容をAIの脳裏に固定しておく。  
それだけで、速度もコストも大きく変わる。

次は、日次コストとモデル別コストだよ。

![日次コストとモデル別コスト](/images/am-magi-platform-launch/daily-cost-and-model-cost.png)

## 🧠 モデル別コストで「誰が燃料を食っているか」を見る

右側のドーナツチャートでは、モデル別のコスト内訳が見える。

今回の例では、主にこの3つだね。

- claude-opus-4-6：$651.07
- claude-sonnet-4-6：$159.90
- claude-haiku-4-5-20251001：$6.73

ほとんどを Opus が占めている。

これは、フラッグシップモデルという巨大なエンジンを、かなり多く使っているということだ。

もちろん、難しい設計や大規模なコード理解には強いモデルが必要になる。  
でも、すべての作業に巨大エンジンを使う必要はない。

買い物に行くだけなのに、毎回ロケットを飛ばす必要はないよね。

軽い修正は Haiku。  
通常の実装は Sonnet。  
難しい設計や複雑なレビューは Opus。

そんなふうにモデルを使い分けられれば、AI開発のコストはもっと賢くなる。

## 🧩 トークン、ブランチ、PRをつなげて見る

次は、トークン内訳、ブランチ別作業時間、PR紐付き工数だよ。

![トークン内訳とブランチ別作業時間](/images/am-magi-platform-launch/token-breakdown-branch-time-pr-effort.png)

左側では、トークンが input / output / cache creation / cache read に分かれている。

今回のデータでは、cache read が 592,113,471。

中央では、ブランチ別の作業時間が見える。

たとえば、

- fix/middleware-to-proxy：4,562分
- claude/elated-booth：3,978分
- main：3,604分
- claude/busy-hopper：2,278分

ブランチごとに、どれくらいAI作業が発生したかがわかる。

これは、AI時代のレトロスペクティブに使える。

「このブランチはなぜ長時間化したのか？」  
「AIに任せすぎていたのか？」  
「人間の設計が曖昧だったのか？」  
「もっと小さいPRに分けられたのか？」

AIのログは、単なる利用記録じゃない。  
開発プロセスを見直すための 地図 なんだ。

右側では、PRに紐づいた作業も見える。  
この例では、PRは12件。  
PRリンクがあるセッションの時間は 7,143分。

AIがPR作成にどれくらい関わっているのか。  
これを見られるのは、チーム開発ではかなり大きい。

## 🤖 Codex の動きも丸ごと見える

MAGI Platform は Claude Code だけじゃない。  
Codex のレポートも見られるようにしているよ。

![Codex レポート](/images/am-magi-platform-launch/codex-report.png)

Codex は、単なるチャットAIというより、実際にコマンドを実行し、パッチを作り、GitHubやMCPと連携する エージェント だ。

だから、見るべき指標も少し違う。

この例では、タスク成功率は 94.3%。  
保存セッション数は 76。  
作業時間は 12,280分。  
総トークンは 471,598,425。

さらに、こんな指標も見える。

- output / reasoning
- exec回数
- patch回数
- GitHub / MCP
- error / abort
- 平均TTFT
- Web検索
- 圧縮回数
- 構造化出力

CodexのようなAIエージェントを見るとき、トークンだけでは足りない。

何回考えたのか。  
何回コマンドを打ったのか。  
何回コードを書き換えたのか。  
どこで失敗したのか。

それを見ないと、AIエージェントという 工場 の稼働状況はわからないんだ。

## 📊 トークン推移と実行元を追う

次は、Codex の日次トークン推移だよ。

![Codex 日次トークン推移](/images/am-magi-platform-launch/codex-daily-token-trend.png)

ここでは、日ごとのトークン量が見える。

4月21日と4月24日に大きな山があるね。  
何か大きな実装や調査が走っていた可能性がある。

下のグラフでは、モデル別、reasoning effort 別、originator / source 別の内訳も見える。

モデル別では gpt-5.4 が大半。  
reasoning effort では xhigh がかなり多い。  
source では Codex Desktop や codex_exec など、どこから動いたのかもわかる。

これは、AIエージェントの 交通量調査 みたいなものだ。

どの道から車が入ってきて、どの道が混雑しているのか。  
それがわかれば、運用を改善できる。

## 🛠️ コマンドとパッチを見る

次は、コマンド・パッチの日次推移だよ。

![コマンド・パッチ日次推移](/images/am-magi-platform-launch/command-patch-daily-trend.png)

Codex のようなエージェントでは、exec_count と patch_count がとても重要だ。

トークンを大量に使っていても、コードがほとんど変わっていないなら、調査や迷走が多かったのかもしれない。  
逆に、patch が多い日は、実際にコード変更が進んだ日かもしれない。

このグラフでは、日ごとにコマンド実行とパッチ適用の回数が見える。

AIがただ考えていただけなのか。  
実際に手を動かしていたのか。

その違いが見えるんだ。

## 🔍 Effort × Duration で重いセッションを見つける

次は、reasoning effort と duration の散布図だよ。

![Effort Duration](/images/am-magi-platform-launch/effort-duration.png)

これは、AIがどれくらい深く考えたかと、どれくらい時間がかかったかを見るグラフだ。

medium effort なのに長時間かかっているセッションがある。  
high effort でも長いものがある。  
low effort は件数が多い。

ここから、いろいろなことが見えてくる。

「この作業は本当に high effort が必要だったのかな？」  
「medium で長時間化しているなら、タスク分割が必要だったのかな？」  
「low effort で十分な作業を、もっと増やせるんじゃないかな？」

AIに仕事を任せるとき、努力量の設定は レバー みたいなものだ。

強く引けば深く考えてくれる。  
でも、そのぶん時間もコストも増える。

だからこそ、effort と duration をセットで見る必要があるんだ。

## ⚠️ エラーはAIエージェントの悲鳴だ

最後に、エラー推移だよ。

![エラー推移](/images/am-magi-platform-launch/error-trend.png)

この例では、4月21日にエラーが増えている。

エラーは、ただの失敗ログじゃない。  
AIエージェントが「ここで詰まったよ」と教えてくれている サイン なんだ。

もし特定の日にエラーが集中しているなら、その日に何が起きたのかを見ればいい。

- 難しいタスクを投げすぎたのか
- リポジトリの状態が悪かったのか
- 権限や環境変数が足りなかったのか
- テストが壊れていたのか
- AIが同じ場所でループしていたのか

エラー推移を見ることで、AIの使い方だけじゃなく、人間側の開発環境も改善できる。

## 🚪 まとめ：AI開発には「可視化」が必要になる

今回の探求をまとめよう。

1．Claude Code や Codex は、開発を大きく加速してくれる  
2．でも、利用が増えるほど、コストやトークンやエラーが見えにくくなる  
3．MAGI Platform は、それらをダッシュボードで可視化する  
4．日次コスト、モデル別コスト、キャッシュ効率、ブランチ別作業時間が見える  
5．Codex では exec、patch、reasoning effort、error まで追える  
6．AIのログは、単なる記録ではなく、開発プロセスを改善するための地図になる  

AIコーディングは、もう個人の便利ツールだけでは終わらない。

これからは、チームの開発基盤になっていく。  
そして、チームの基盤になるなら、そこには必ず 観測 と 統制 が必要になる。

でも、怖がらなくていい。

見えないものは怖い。  
でも、見えるようになれば、改善できる。

MAGI Platform は、AI開発という新しい海を進むためのコンパスだよ。

君はもう、AIをただ使うだけのユーザーじゃない。  
AIチームを設計し、観測し、改善する アーキテクト なんだ。

それじゃあ、また次の探求で会おう！
