# Claude API コスト最適化 — プロンプトキャッシング完全ガイド

Claude APIを使ってLLMアプリを開発していると、ある時点で必ず直面する問題がある。**「API費用、思ったより高くない？」**という問題だ。

この問題を解決するのが「**プロンプトキャッシング（Prompt Caching）**」だ。Anthropicが公式に提供するこの機能を正しく使えば、**APIコストを最大90%削減**できる。

本記事では、プロンプトキャッシングの仕組みから実装コード、コスト削減の計算方法まで、すぐに使えるレベルで解説する。

## プロンプトキャッシングとは

プロンプトキャッシングは、**Anthropicが2024年8月に導入した公式のコスト最適化機能**だ。

通常、APIリクエストでは毎回すべてのトークン（システムプロンプト・ドキュメント・会話履歴）に対して入力料金が発生する。同じ10,000トークンのシステムプロンプトを100回送れば、100回分のコストがかかる。

プロンプトキャッシングを使うと、**2回目以降の同じコンテンツは「キャッシュから読み込み」扱い**になり、通常の入力料金の10分の1（90%オフ）で処理される。

**対応モデル（2026年5月時点）:**

| モデル | 対応 |
|-------|------|
| Claude 3.5 Sonnet | ✅ |
| Claude 3.5 Haiku | ✅ |
| Claude 3 Opus | ✅ |
| Claude 3 Haiku | ✅ |

## 仕組みの詳細：キャッシュ書き込みと読み込み

プロンプトキャッシングには「**書き込み（Cache Write）**」と「**読み込み（Cache Read）**」の2つのフェーズがある。

### 料金体系

| 操作 | 料金倍率 | 意味 |
|------|---------|------|
| 通常の入力トークン | × 1.0 | ベースライン |
| キャッシュ書き込み | × 1.25 | 初回：少し高い |
| キャッシュ読み込み | × 0.1 | 2回目以降：90%オフ |

最初にキャッシュを「書き込む」ときは通常より25%高くなる。しかし2回目以降は通常の10分の1になるため、**2〜3回以上使えば元が取れる**計算になる。

### キャッシュの有効期限

キャッシュの有効期限は**5分間**。ただし5分以内に同じキャッシュを使ったリクエストが来ると、有効期限が5分延長される。連続して使い続ける限り、キャッシュは維持され続ける。

### 最小キャッシュサイズ

キャッシュが有効になるには、コンテンツが一定のトークン数以上である必要がある。

| モデル | 最小トークン数 |
|-------|--------------|
| Claude 3.5 Sonnet / 3.5 Haiku | 1,024トークン以上 |
| Claude 3 Opus / 3 Haiku | 2,048トークン以上 |

これ未満の内容に `cache_control` を設定しても、キャッシュは適用されない。

## 実装方法：コードで見るプロンプトキャッシング

プロンプトキャッシングの実装は、コンテンツブロックに `"cache_control": {"type": "ephemeral"}` を追加するだけだ。

### パターン1: システムプロンプトのキャッシュ（最も基本）

```python
import anthropic

client = anthropic.Anthropic()

# 長いシステムプロンプトをキャッシュする
response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": """あなたはECサイトのカスタマーサポート担当AIです。
以下のルールに従って対応してください：

# 対応ルール（2,000字以上の詳細な指示）
1. 挨拶は「いらっしゃいませ」から始める
2. 返品ポリシーは〇〇日以内...
（以下、長い指示が続く）""",
            "cache_control": {"type": "ephemeral"}  # ← これを追加するだけ
        }
    ],
    messages=[
        {"role": "user", "content": "注文のキャンセルはできますか？"}
    ]
)
```

`cache_control` を付けたブロックまでのコンテンツが、次回以降キャッシュから読み込まれる。

### パターン2: 大容量ドキュメントのキャッシュ

RAGやドキュメントQ&Aのアプリでは、毎回大きなドキュメントを渡すパターンが多い。これがコスト爆発の原因になりやすい。

```python
# 製品マニュアル全文（10,000〜50,000トークン）をキャッシュ
with open("product_manual.txt", "r") as f:
    manual_content = f.read()

response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    max_tokens=2048,
    system=[
        {
            "type": "text",
            "text": "あなたは製品マニュアルに基づいて質問に答えるAIです。"
        },
        {
            "type": "text",
            "text": f"<manual>\n{manual_content}\n</manual>",
            "cache_control": {"type": "ephemeral"}  # マニュアル全文をキャッシュ
        }
    ],
    messages=[
        {"role": "user", "content": "バッテリーの交換方法を教えてください"}
    ]
)
```

マニュアルが50,000トークンあっても、2回目以降は通常コストの10%で処理される。

### パターン3: マルチターン会話でのキャッシュ

会話が長くなるほど、過去のやりとりがコンテキストに蓄積されコストが増える。会話履歴もキャッシュできる。

```python
# 会話履歴を蓄積しながら、適切な位置にキャッシュポイントを設ける
messages = [
    {"role": "user", "content": "今日の売上を教えて"},
    {"role": "assistant", "content": "今日の売上は〇〇円です..."},
    # ... 過去のやりとり
    {
        "role": "user",
        "content": [
            {
                "type": "text",
                "text": "先ほどの話を踏まえて、来週の施策を提案して",
                "cache_control": {"type": "ephemeral"}  # ここまでをキャッシュ
            }
        ]
    }
]
```

## コスト削減シミュレーション

実際にどれくらい削減できるか、具体的なシナリオで計算してみよう。

**前提: Claude 3.5 Sonnetの料金**
- 通常入力: $3.00 / 100万トークン
- キャッシュ書き込み: $3.75 / 100万トークン（× 1.25）
- キャッシュ読み込み: $0.30 / 100万トークン（× 0.1）

### シナリオA: カスタマーサポートBot（1日100リクエスト）

- システムプロンプト: 5,000トークン
- 1日のリクエスト数: 100件

**キャッシュなし:**
5,000トークン × 100件 = 500,000トークン/日
= $1.50/日 → **$45/月**

**キャッシュあり（5分以内に連続リクエストあり）:**
キャッシュ書き込み: 5,000 × $3.75 = $0.01875（初回のみ）
キャッシュ読み込み: 5,000 × 99件 × $0.30 = **$0.1485/日**
= **約$4.5/月**

→ **削減率: 90%、月$40.5の節約**

### シナリオB: ドキュメントQ&A（20,000トークンの仕様書）

- ドキュメントサイズ: 20,000トークン
- 1日のリクエスト数: 50件

**キャッシュなし:** 20,000 × 50 = 1,000,000トークン/日 = **$3.00/日**

**キャッシュあり:** 20,000（書き込み）+ 20,000 × 49（読み込み × 0.1）
≈ 20,000 × 1.25 + 20,000 × 49 × 0.1 = 25,000 + 98,000 = 123,000トークン相当/日
= **$0.369/日**

→ **削減率: 87.7%**

### 損益分岐点の計算式

同じキャッシュを何回使えば元が取れるか：

```
損益分岐回数 ≈ 1.25 / (1 - 0.1) = 約1.4回
```

つまり**2回以上同じキャッシュを使えば、必ず利益になる**。リクエストが連続する用途ならほぼ確実にコスト削減できる。

## ベストプラクティス

### 1. キャッシュしやすいコンテンツを選ぶ

プロンプトキャッシングが最も効果的なのは、**変化しないコンテンツ**だ。

✅ **キャッシュに向いているもの:**
- システムプロンプト（AIのキャラクター設定・指示文）
- ドキュメント・マニュアル・仕様書
- ツール定義（Function Calling のスキーマ）
- Few-shot examples（例示）

❌ **キャッシュに向かないもの:**
- ユーザーごとに変わる動的な情報
- リクエストのたびに内容が変わる文章

### 2. 設計原則「固定を前に、変動を後ろに」

プロンプトキャッシングは「前から数えて同じプレフィックス」をキャッシュする仕組みだ。**変わらないコンテンツは前半に、変わるコンテンツは後半に配置する**のが鉄則。

```
【良い例】
[前半・固定] システムプロンプト (cache_control あり)
[後半・変動] ユーザーの質問 (毎回変わる)

【悪い例】
[前半・変動] 今日の日付や動的情報 ← キャッシュが効かない
[後半・固定] システムプロンプト
```

コンテキストの途中で変動コンテンツが入ると、それ以降はすべてキャッシュが無効になる。

### 3. 最小トークン数を意識する

1,024トークン未満のシステムプロンプトに `cache_control` を付けても効果はない。短いシステムプロンプトはキャッシングより、**プロンプト自体を短くすること**で最適化したほうがいい。

## 注意点・よくある落とし穴

### 落とし穴1: キャッシュの5分切れ

5分以上間隔が空いたリクエストではキャッシュが失効し、再書き込みが発生する。**リクエストが散発的（5分以上の間隔がある）場合は効果が薄い**。使用頻度が高いアプリほど効果が大きい。

### 落とし穴2: プレフィックスの一致が必要

Claudeのキャッシュは「先頭からN文字が一致する」ことで同一キャッシュと判断する。ほんの少しでもシステムプロンプトを変更すると、別のキャッシュ書き込みが発生してしまう。

**NG例:**
```python
# 毎回タイムスタンプをシステムプロンプトに入れる → キャッシュが効かない
system_prompt = f"現在時刻は{datetime.now()}です。あなたは..."
```

### 落とし穴3: 対応モデルの確認

プロンプトキャッシングは旧世代モデル（Claude 2など）には対応していない。モデルをアップデートする際は事前に確認しよう。

## まとめ

プロンプトキャッシングのポイントを整理する。

| ポイント | 内容 |
|---------|------|
| **効果** | キャッシュ読み込み時のコストが通常の10%に |
| **実装** | `"cache_control": {"type": "ephemeral"}` を追加するだけ |
| **損益分岐** | 2回以上使えば必ずコスト削減になる |
| **最適な用途** | 長いシステムプロンプト・大容量ドキュメント・ツール定義 |
