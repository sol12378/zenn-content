# Claude Code Agent Teams でLLM品質を自動検証する

## はじめに

LLMの業務活用が急速に拡大する中、**LLMの出力品質をどう監視するか**は、導入企業の最大の課題です。

生成されたテキスト・データが正確か、ハルシネーション（幻想的な情報生成）がないか、ビジネスロジックに沿っているか——これらを人手で確認していては、AI導入の効率メリットが損なわれます。

特に**エージェント（複数のツールを駆使して問題を解決するAI）**を導入する場合、データベース更新・APIコール・財務計算など、各ステップでの品質監視が必須です。

本記事では、**Claude Code Agent Teams** を活用して、LLM出力を自動検証するパイプラインを構築する方法を、実装例を交えて解説します。

## LLMの出力品質が見過ごされる理由

まず、なぜ企業でLLM品質の問題が後回しにされるのか、3つの失敗事例から整理しましょう。

### 失敗事例1: 単一エージェントの盲目的信頼
あるメーカーのデータ分析チームは、ChatGPTでCSVを集計させていました。数ヶ月後、集計ロジックが「売上の重複カウント」を含んでいたことに気づきました。経営層へのレポートが誤った数字で出ていたため、経営判断に悪影響を与えてしまいました。

**原因**: 単一のLLMに全て委ねており、出力の正当性を検証する仕組みがなかった。

### 失敗事例2: 品質チェックの遅延
ある金融機関は、LLMで顧客データから与信判定文を生成していました。品質チェックは「営業が目視確認」という手作業だったため、チェック遅延が慢性化し、最終的に不正な与信文書が出社していました。

**原因**: データ品質管理と品質チェックが分離されており、フィードバックループが機能しなかった。

### 失敗事例3: 複数LLMでの一貫性欠如
ある流通企業は、「商品説明の自動生成」にClaude、「在庫最適化の推奨」にGPT、「顧客応対」にBertを使い分けていました。しかし各LLMの出力フォーマットが異なり、データパイプラインでの統合時にエラーが頻発しました。

**原因**: 複数のLLMを独立して運用しており、**出力の一貫性を検証する共通スキーム**がなかった。

## Claude Code Agent Teams での品質検証の仕組み

これらの失敗を防ぐため、**複数のエージェントによる分散検証** が有効です。

### Agent Teams とは

Claude Code Agent Teams は、複数の専門的なエージェント（Agent）を協調させ、複雑なタスクを自動化するフレームワークです。各エージェントは独立した「役割」を持ち、相互にデータやレポートを受け渡します。

```
入力データ
  ↓
┌─────────────────────────────────────┐
│ データ抽出エージェント               │
│ （CSVを解析し、構造化データに変換）  │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│ 品質検証エージェント（複数）          │
│ ・形式妥当性チェック               │
│ ・ビジネスルール検証               │
│ ・異常値検知                      │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│ スコアリングエージェント             │
│ （品質スコア = 各検証結果の集約）   │
└──────────────┬──────────────────────┘
               ↓
出力（品質スコア + アラート）
```

### なぜ複数エージェントが効果的か

1. **独立した視点**: 各エージェントが異なる検証軸（形式・ビジネスロジック・異常値など）を担当するため、単一のLLMでは見落としやすい問題を検出できます。

2. **スケーラビリティ**: 検証ルールが増えても、新しいエージェントを追加するだけ。既存のパイプラインに影響しません。

3. **説明責任**: 「なぜこのデータが拒否されたのか」を各エージェントの判断理由で追跡可能。AIの意思決定を「ブラックボックス化」させません。

4. **品質スコアの可視化**: 各ステップの検証結果を数値化でき、KPI化して経営層にも報告できます。

## 実践例：EC サイトの商品説明自動生成

ここから、**具体的なユースケース**で、Agent Teams による品質検証パイプラインを見てみましょう。

### ユースケース: EC サイトの商品説明自動生成

ある大手ECプラットフォームは、毎日1,000件の商品をAPIで取り込み、商品説明を自動生成する仕組みを構築することにしました。

**品質管理の課題**:
- 商品名が正確に反映されているか
- 商品特性（素材・サイズ・色など）が漏れていないか
- 不適切な表現（過度な修飾、事実でない主張）がないか
- JSON形式での出力が正確か

これらを人手でチェックしていては、1,000件の処理に数日かかります。

### Agent Teams による自動検証パイプライン

```python
# 疑似コード

class CommerceQualityPipeline:
    """
    商品説明の品質検証パイプライン
    複数エージェントが協調して品質を検証
    """

    def __init__(self):
        # 各検証エージェントを初期化
        self.description_generator = Agent(model="claude-opus", role="description_generator")
        self.validator_format = Agent(model="claude-3.5-sonnet", role="format_validator")
        self.validator_business = Agent(model="claude-3.5-sonnet", role="business_logic_validator")
        self.validator_safety = Agent(model="claude-3.5-sonnet", role="safety_validator")
        self.scorer = Agent(model="claude-3.5-sonnet", role="quality_scorer")

    def process_product(self, product_data):
        """
        商品1件をパイプラインで処理
        """

        # Step 1: 説明文の生成
        description = self.description_generator.run(
            prompt=f"""商品データから説明文を生成してください。
            商品ID: {product_data['id']}
            商品名: {product_data['name']}
            カテゴリ: {product_data['category']}
            仕様: {product_data['spec']}

            出力形式:
            {{"description": "説明文", "keywords": ["キーワード1", "キーワード2"]}}
            """
        )

        # Step 2: 形式妥当性チェック（JSON形式、必須フィールド等）
        format_check = self.validator_format.run(
            prompt=f"""以下の出力が正しいJSON形式か、必須フィールドを含むか検証してください。
            出力: {description}

            検証結果を以下の形式で返してください:
            {{"is_valid": true/false, "errors": ["エラー1", "エラー2"]}}
            """
        )

        if not format_check['is_valid']:
            return {
                "product_id": product_data['id'],
                "quality_score": 0,
                "status": "rejected",
                "reason": f"形式エラー: {format_check['errors']}"
            }

        # Step 3: ビジネスルール検証
        business_check = self.validator_business.run(
            prompt=f"""以下の説明文が、商品の主要特性をカバーしているか確認してください。
            商品名: {product_data['name']}
            商品仕様: {product_data['spec']}
            生成説明文: {description['description']}

            チェック項目:
            - 商品名が説明文に含まれているか
            - 主要素材・サイズが記載されているか
            - 価格帯や適用範囲が明示されているか

            結果: {{"coverage": 0-100, "missing_items": ["項目1", "項目2"]}}
            """
        )

        # Step 4: 安全性チェック（不当な主張、差別表現等）
        safety_check = self.validator_safety.run(
            prompt=f"""以下の説明文に、不適切な表現がないか確認してください。
            説明文: {description['description']}

            チェック項目:
            - 医療効果・法的根拠なき主張
            - 差別的表現
            - 誇大広告（根拠なき「最高」「唯一」等）
            - 事実に反する記述

            結果: {{"is_safe": true/false, "issues": ["問題1", "問題2"]}}
            """
        )

        # Step 5: 総合スコアリング
        quality_score = self.scorer.run(
            prompt=f"""複数の検証結果から、商品説明の総合品質スコア（0-100）を算出してください。

            検証結果:
            - 形式妥当性: {format_check}
            - ビジネス対応率: {business_check['coverage']}
            - 安全性: {safety_check['is_safe']}

            スコア計算式:
            - 形式OK: +25点
            - ビジネス対応率 > 80%: +35点
            - 安全性OK: +40点

            結果: {{"score": 0-100, "recommendation": "approved/review_needed/rejected"}}
            """
        )

        return {
            "product_id": product_data['id'],
            "quality_score": quality_score['score'],
            "status": quality_score['recommendation'],
            "validation_details": {
                "format": format_check,
                "business": business_check,
                "safety": safety_check
            }
        }

# 実行例
pipeline = CommerceQualityPipeline()
products = load_products_from_api()

results = []
for product in products:
    result = pipeline.process_product(product)
    results.append(result)

    if result['quality_score'] < 70:
        alert_team(f"商品 {product['id']}: 品質スコア {result['quality_score']} - 手動確認が必要")

# 品質スコアの集計
avg_score = sum(r['quality_score'] for r in results) / len(results)
print(f"本日の平均品質スコア: {avg_score}")
```

### 実装のポイント

1. **エージェント間のデータ受け渡し**: 各エージェントの出力（JSON形式）を次のエージェントの入力として自動パイプライン化

2. **並列処理**: 形式検証・ビジネス検証・安全性検証は互いに独立しているため、複数エージェントを並列実行可能

3. **品質メトリクスの数値化**: 「品質スコア」として KPI 化し、経営層への報告資料として活用

## データ品質管理へのフィードバックループ

品質スコアが単なる「指標」にとどまっていては、意味がありません。**実装深度を高めるため**には、フィードバックループを回す必要があります。

### LLM品質検証から組織的な改善へ

```
品質スコア（定量データ）
  ↓
「なぜスコアが低いのか」の分析
  ↓
エージェントの検証ルールの改善
  ↓
LLMプロンプトの最適化
  ↓
再度パイプラインで検証
  ↓
スコア向上の確認
```

各エージェントの判断理由がログとして記録されるため、「形式エラーが多い」「商品特性の抜け漏れが頻繁」など、具体的な改善ポイントが可視化されます。

## AI品質監査への展開：MAGI Audit への自然な橋渡し

ここで注目すべき点は、**複数エージェントによる分散検証の仕組み** は、単なる「LLM出力の品質チェック」にとどまらないということです。

実は、この考え方は **AI品質監査（AI Audit）** という、より広い分野に応用できます。

### AI品質監査とは

AI品質監査とは、LLMやエージェントが生成・判定したデータ全体に対し、第三者的な視点から「その判定は妥当か？」「ビジネスリスクはないか？」を継続的に監視する仕組みです。

- **適合性監視**: 企業ポリシー・法令遵守に沿っているか
- **性能監視**: 意図した精度が保たれているか
- **リスク監視**: 事業上の重大な誤りが発生していないか

これは、単一のLLMに依存した「泥縄式の品質チェック」ではなく、**組織全体での AI 信頼性運用**へのステップアップです。

このような「複数エージェントによる多軸的な品質検証」の考え方を、より体系的に、より詳細に、より統合的に実装するためのプラットフォームが必要です。そこで活躍するのが、**MAGI Audit** のような AI品質監査プラットフォームです。

本記事で示したパイプラインを「コード化された実装」とすれば、MAGI Auditはそれを「組織的な運用フレームワーク」として拡張し、複数部門・複数LLMの品質を統一的に監視する仕組みを提供します。

## まとめ

Claude Code Agent Teams を使うことで、以下が実現できます：

- ✅ **複数視点からの自動検証**: 形式・ビジネスロジック・安全性を、エージェントが独立して検証
- ✅ **品質スコアの可視化**: 経営層にも理解しやすい数値で品質を報告
- ✅ **スケーラビリティ**: 検証ルール増加に対応しやすい、拡張可能な設計
- ✅ **説明責任**: AI の判断理由がログとして記録され、信頼性が向上

LLM活用の成功は、**出力品質の継続的な監視** にかかっています。ぜひこのパターンを参考に、あなたの組織でも自動検証パイプラインの構築を検討してみてください。
